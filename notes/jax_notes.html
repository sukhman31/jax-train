JAX Learning — Exercises 1 & 2

Study Notes

Notes compiled from building an MLP from scratch and implementing a custom pytree class — covering transform composition, vmap batching, gradient averaging, and the flatten/unflatten contract.

Core transforms

JAX has three primary transforms. Each is a function transformation — it takes a function and returns a new function.

TransformWhat it doesWorks on
jax.grad(f)Returns gradient of f w.r.t. first argSingle sample
jax.jit(f)Compiles f via XLA — fast after first callAnything
jax.vmap(f)Batches f over an array axis automaticallySingle sample → batch
Key insight
All three compose freely. You can wrap them in any order — each one just sees a function and returns a function.

Pytrees

A pytree is any nested structure JAX can flatten into a list of arrays and unflatten back. Built-in nodes: list, dict, tuple. Custom classes need registration.

TypeJAX sees it as
{"w1": arr, "b1": arr}Node — walks inside
[arr1, arr2]Node — walks inside
jnp.array(...)Leaf — stops here
(2, 3) tuple of intsNode — walks inside (gotcha!)

Tracing

When jit runs your function the first time, it replaces inputs with abstract tracers — placeholders that know shape and dtype but carry no values. JAX records every operation into a computation graph, then XLA compiles that graph.

Gotcha
if jnp.sum(x) > 0 fails inside jit — the comparison produces a traced bool, not a real one. Use jnp.where or lax.cond instead.

Static vs traced

import numpy as np       # static — stays in Python, compile-time
import jax.numpy as jnp  # traced — becomes part of the graph

# x.shape is static — safe to use in range()
for i in range(x.shape[0]): ...  # ✅

# jnp.array(x.shape) is traced — can't use in range()
for i in range(jnp.array(x.shape).prod()): ...  # ❌

Exercise 1 — MLP architecture

The network takes a (2,) input and produces a (2,) output via a hidden layer of 4 neurons.

Params dict — shapes explained

params = {
    "w1": shape (4, 2),   # 4 hidden neurons, each connected to 2 inputs
    "b1": shape (4,),      # one bias per hidden neuron
    "w2": shape (2, 4),   # 2 outputs, each connected to 4 hidden neurons
    "b2": shape (2,),      # one bias per output neuron
}

Forward pass — shape flow

def forward(x, params):
    # x: (2,)
    h = jax.nn.relu(jnp.dot(params["w1"], x) + params["b1"])
    # (4,2)@(2,) + (4,) → (4,)
    y = jnp.dot(params["w2"], h) + params["b2"]
    # (2,4)@(4,) + (2,) → (2,)
    return y

Transform composition order

Build inside-out. Each layer wraps the one inside it:

loss(params, x, target) ← single sample, returns scalar
↓ wrap with grad
grad_fn(params, x, target) ← single sample, returns gradients
↓ wrap with vmap
batch_grad_fn(params, xs, targets) ← whole batch
↓ wrap with jit
jit_grad(params, xs, targets) ← whole batch, compiled 
grad_fn       = jax.grad(loss, argnums=2)
batch_grad_fn = jax.vmap(grad_fn, in_axes=(0, 0, None))
jit_grad      = jax.jit(batch_grad_fn)
Why this order
jit(vmap(grad)) compiles the entire batched computation as one graph. Reversing to vmap(jit(grad)) compiles each sample separately — N compiled calls instead of one.

in_axes — mapping arguments to batch axes

in_axes is a tuple with one value per function argument. It tells vmap how to handle each one:

ValueMeaning
0Slice along axis 0 — one slice per batch element
1Slice along axis 1
NoneDon't slice — same value for every batch element
# grad_fn(params, x, target)
jax.vmap(grad_fn, in_axes=(None, 0, 0))
#                    ↑      ↑    ↑
#                 params    x  target
#                 shared  batch batch
Common mistake
Getting the order wrong — in_axes=(0, 0, None) would try to slice params along axis 0, which slices into the weight matrices. The error message says "vmap got inconsistent sizes for array axes to be mapped" and lists your param shapes as evidence.

Averaging gradients across the batch

Because you vmapped over the batch, jit_grad returns one gradient per sample — an extra batch dimension on every array:

# params["w1"] shape: (4, 2)
# grads["w1"]  shape: (10, 4, 2)  ← extra batch dim from vmap

# Can't subtract directly — shapes don't match
# Must average first:
mean_grads = jax.tree.map(lambda g: jnp.mean(g, axis=0), grads)
# mean_grads["w1"] shape: (4, 2)  ← back to param shape

jax.tree.map walks the entire dict and applies the function to every leaf — no need to handle each key separately.

Full training loop

lr = 0.01
batch_loss = jax.jit(jax.vmap(loss, in_axes=(0, 0, None)))

for i in range(num_steps):
    grads = jit_grad(xs, targets, params)
    mean_grads = jax.tree.map(lambda g: jnp.mean(g, axis=0), grads)
    params = jax.tree.map(lambda p, g: p - lr * g, params, mean_grads)

    if i % 10 == 0:
        losses = batch_loss(xs, targets, params)
        print(f"step {i}  loss {jnp.mean(losses):.4f}")
What to watch
Mean loss should decrease each print. If it goes up, your learning rate is too high. If it barely moves, it's too low. Try values between 0.001 and 0.1.

Exercise 2 — Custom pytree

For JAX to transform through a custom class, it needs to know how to break it apart and put it back together.

The three buckets

BucketWhat goes inJAX behaviour
LeavesArrays to transformDifferentiated, compiled, batched
AuxStatic metadataFrozen at trace time, handed back to unflatten
NeitherTransient dataDropped — gone after any transform

Implementation

@jax.tree_util.register_pytree_node_class
class Parameter:
    def __init__(self, value, name: str, frozen: bool = False):
        self.value  = value    # array  → leaf
        self.name   = name     # string → aux
        self.frozen = frozen   # bool   → aux

    def tree_flatten(self):
        leaves = (self.value,)
        aux    = (self.name, self.frozen)
        return leaves, aux

    @classmethod
    def tree_unflatten(cls, aux, leaves):
        name, frozen = aux
        value,       = leaves
        return cls(value, name, frozen)
Aux must be hashable
JAX uses aux as part of its JIT cache key. Tuples of strings and bools are fine. Lists and arrays are not — they'll raise a TypeError.

Why grad returns a Parameter, not an array

It's the unflatten function that rebuilds the object — grad itself knows nothing about Parameter.

input Parameter(value=[1,2,3], name="weights")
↓ tree_flatten
leaves=[[1,2,3]] aux=("weights", False)
↓ grad differentiates leaves
leaves=[[2,4,6]] aux=("weights", False) ← same aux
↓ tree_unflatten
output Parameter(value=[2,4,6], name="weights")

JAX stores the aux from step 1 and passes it directly to unflatten in step 4. That's how the name and frozen flag survive — they never went through differentiation at all.

What we're differentiating with respect to

When you call grad(f)(p) where p is a Parameter, you differentiate w.r.t. all leaves of p.

p = Parameter(jnp.array([1., 2., 3.]), name="weights")

# leaves = [array([1., 2., 3.])]  ← differentiated
# aux    = ("weights", False)      ← invisible to grad

grad(lambda p: jnp.sum(p.value ** 2))(p)
# ∂/∂value [ sum(value²) ] = 2 * value = [2., 4., 6.]

If your class had two array fields, grad would return a Parameter where both fields hold their respective gradients — one gradient value per leaf.

General rule
grad differentiates w.r.t. all leaves of the input pytree. Aux is completely invisible to it.

JAX Rules Reference

Expanded notes with worked examples, compiled while porting batran-lib to JAX/Flax NNX.

The two-phase mental model

Every jitted function runs in two distinct phases, and almost every JAX gotcha is a direct consequence of this split.

call 1 TRACE (Python actually executes, building a graph) → COMPILE (XLA takes the graph)
call 2+ COMPILED VERSION RUNS — Python code is never executed again 
import jax

def f(x):
    print("tracing!")   # only prints on call 1
    return x * 2

jf = jax.jit(f)
jf(jnp.array(1.0))   # prints "tracing!", then returns 2.0
jf(jnp.array(2.0))   # prints nothing — runs compiled version, returns 4.0
jf(jnp.ones((3,)))   # NEW shape → retraces → prints "tracing!" again, returns [2,2,2]
Key insight
A jitted function is retraced (and recompiled) whenever it sees a new input shape or dtype — this is why "shapes must be static" is rule #1 for jit.

Purity — the rule everything derives from

Functions passed to jit, grad, or vmap must be pure: same inputs always produce the same outputs, no mutation of inputs, no reading/writing global state, no side effects that matter to the result.

# ❌ impure — reads global state
counter = 0
def f(x):
    global counter
    counter += 1              # side effect!
    return x + counter

# under jit, "counter" only increments during the TRACE call.
# every subsequent call reuses the value baked in at trace time.
jf = jax.jit(f)
jf(1.0)  # traces: counter becomes 1 → returns 2.0
jf(1.0)  # compiled version: "+counter" is frozen at 1 → returns 2.0 again (not 3.0!)
Why this matters
This is the classic silent bug: no error is raised, the function just quietly stops reflecting the global's real value after the first call.

Control flow — the most common gotcha

Ask yourself: does this if/while/for depend on an array value, or on a shape / Python scalar?

Condition depends onPlain PythonJAX equivalent
Array value (e.g. x[0] > 0)❌ fails under jit/grad/vmapjnp.where, lax.cond, lax.while_loop
Shape / dtype✅ fineplain Python fine (shapes are static)
Python int / bool (not a JAX array)✅ fineplain Python fine
# ❌ fails — comparison produces a traced bool, unknown at trace time
def f(x):
    if x[0] > 0:
        return x * 2
    return x
# TracerBoolConversionError: attempted boolean conversion of traced array

# ✅ element-wise branching with jnp.where
def f(x):
    return jnp.where(x > 0, x * 2, x)

# ✅ shape is known at trace time (it's Python metadata, not a value)
def f(x):
    if x.shape[0] > 4:
        return x[:4]
    return x
How to remember it
Shapes are compile-time facts — every trace of a given shape takes the same branch, so Python if is safe. Array values are only known at run time — Python can't branch on something that doesn't exist yet.

lax control-flow equivalents

from jax import lax

# lax.cond — if/else on an array value, both branches must return same shape/dtype
lax.cond(x > 0,
         lambda x: x * 2,   # true_fn
         lambda x: x,       # false_fn
         x)

# lax.while_loop — dynamic-length loop (number of iterations not known ahead)
def cond_fn(state):
    i, x = state
    return x < 100          # keep looping while x < 100

def body_fn(state):
    i, x = state
    return (i + 1, x * 2)

final_i, final_x = lax.while_loop(cond_fn, body_fn, (0, 1.0))

# lax.fori_loop — for loop with known/dynamic bounds, simpler than while_loop
result = lax.fori_loop(0, 10, lambda i, x: x + i, 0)

# lax.scan — for loop that ALSO collects outputs at each step (prefer over fori_loop)
def step(carry, x):
    new_carry = carry + x
    return new_carry, new_carry   # (next carry, value to stack into output)

final_carry, all_outputs = lax.scan(step, 0, jnp.arange(5))
# final_carry = 10 (0+0+1+2+3+4)
# all_outputs = [0, 1, 3, 6, 10]  ← running sum at each step
Why lax.scan over a Python for-loop
A Python for loop over N steps unrolls into N copies of the op graph at trace time — slow to compile, huge graph. lax.scan compiles the loop body once and reuses it, exactly like a real loop.

Random keys — always explicit

JAX has no hidden global random state (unlike numpy.random). Every call that needs randomness takes an explicit key, and a key must never be reused.

key = jax.random.key(0)
key1, key2 = jax.random.split(key)   # split BEFORE every use

a = jax.random.normal(key1, (3,))
b = jax.random.normal(key2, (3,))
# a and b are different, independent random arrays

# ❌ reusing the same key for two draws gives IDENTICAL output
a = jax.random.normal(key, (3,))
b = jax.random.normal(key, (3,))
# a == b  — not what you want!
In this codebase
This is exactly what nnx.Rngs(0) manages for you — rngs.params() and rngs.dropout() each hand out a fresh split key automatically, so you never split by hand inside a Flax NNX module.

No in-place mutation

# ❌ JAX arrays are immutable — no item assignment
x = jnp.array([1., 2., 3.])
x[0] = 9.   # TypeError: '<class 'jaxlib.Array'>' object does not support item assignment

# ✅ .at[].set() returns a NEW array with the update applied
x = x.at[0].set(9.)        # [9., 2., 3.]
x = x.at[1].add(10.)       # [9., 12., 3.]
x = x.at[0:2].multiply(2.)   # [18., 24., 3.]

# same idea for dicts of params — never mutate, always rebuild
params = {**params, "w": params["w"].at[0].set(1.0)}
Why immutability
Purity requires it — if arrays could mutate in place, the same input could silently produce different outputs across calls, and XLA couldn't safely reorder/fuse operations during compilation.

Integers will silently break grad

# ❌ integer array — grad returns zeros, NO error is raised
params = {"w": jnp.array([1, 2, 3])}       # dtype: int32
grad_fn = jax.grad(lambda p: jnp.sum(p["w"].astype(jnp.float32) ** 2))
# works, but if you differentiate w.r.t. the int array directly, JAX either
# errors or (in some versions) silently gives meaningless gradients

# ✅ float array — differentiable, behaves as expected
params = {"w": jnp.array([1.0, 2.0, 3.0])}   # dtype: float32

# always initialise params with float-producing constructors:
jnp.zeros(4)                       # float32 by default
jnp.ones(4)                        # float32 by default
jax.random.normal(key, (4,))       # float32 by default
Where this bit us
Token ids (token_ids_batch in embedding.py) are correctly kept as int — they're indices, never differentiated. Only the embedding table itself (nnx.Param, float) needs a gradient. Don't confuse "this array is used for indexing" with "this array needs to be float".

Composition order — worked example

# standard order: grad innermost, vmap middle, jit outermost
loss_fn        = lambda params, x, y: jnp.sum((forward(params, x) - y) ** 2)
grad_fn        = jax.grad(loss_fn, argnums=0)                       # single sample → grad
batched_grad   = jax.vmap(grad_fn, in_axes=(None, 0, 0))         # whole batch
fast_batched   = jax.jit(batched_grad)                            # compiled

# jit(vmap(grad(fn))) compiles ONE fused graph for the whole batch.
# vmap(jit(grad(fn))) would compile N separate calls — one per sample — much slower.

Follow-up Q&A

Questions that came up re-reading this code after time away — kept close to how they were actually asked.

argnums vs in_axes — what's the difference?

def loss(x, target, params):
    ...
    return scalar_loss

grad_fn       = jax.grad(loss, argnums=2)
batch_grad_fn = jax.vmap(grad_fn, in_axes=(0, 0, None))

argnums=2 tells grad which single argument to differentiate w.r.t., by position — here, params (index 2 of x, target, params). grad_fn(x, target, params) returns a gradient shaped like params only.

in_axes=(0, 0, None) tells vmap how to treat every argument when batching, in the same order as grad_fn's signature:

PositionValueMeaning
x0slice along axis 0 — one sample per vmap iteration
target0same — batch of targets
paramsNonedon't slice — reuse the identical params for every sample
The core distinction
argnums picks one argument to differentiate against — grad only ever computes derivatives of one thing. in_axes describes every argument's batching behavior, because vmap needs to know how to handle each one individually — batch it, or broadcast it unchanged.

Is "10" the batch size or the number of samples?

They're the same thing — a "batch of 10" and "10 samples" mean identical: 10 separate training examples stacked into one array. The confusion comes from conflating sample (one data point, e.g. one (x, y) pair) with batch (a collection of samples processed together).

# xs shape (10, 2)      → 10 samples, each a (2,) vector
# targets shape (10, 2) → 10 samples, each a (2,) target vector
# "batch size" = 10 = how many samples are grouped into this one array

# what grad_fn expects (single sample):
grad_fn(x, target, params)          # x: (2,), target: (2,)

# what vmap(grad_fn, in_axes=(0,0,None)) does conceptually, for i in range(10):
grad_fn(xs[i], targets[i], params)  # 10 separate calls, stacked into shape (10, ...)
Why the mean afterward
vmap doesn't literally write a Python loop — it vectorizes at the XLA level — but that's the right mental model: axis 0 is "which sample," and the output gradient gets a new leading axis of size 10, one gradient per sample, not yet averaged. That's why the training loop does jax.tree.map(lambda g: jnp.mean(g, axis=0), grads) right after — to collapse the per-sample axis back to a single gradient matching params' shape.

grad on a custom pytree with two array fields — worked numbers

Parameter isn't a mathematical function, so it's never "differentiated" itself — grad only ever differentiates the arithmetic done on the arrays inside it. The class is just packaging; registration tells JAX where the real numbers live.

@jax.tree_util.register_pytree_node_class
class Parameter:
    def __init__(self, value, momentum, name, frozen=False):
        self.value = value        # array → leaf
        self.momentum = momentum  # array → leaf
        self.name = name          # string → aux
        self.frozen = frozen      # bool → aux

    def tree_flatten(self):
        return (self.value, self.momentum), (self.name, self.frozen)

    @classmethod
    def tree_unflatten(cls, aux, leaves):
        name, frozen = aux
        value, momentum = leaves
        return cls(value, momentum, name, frozen)

p = Parameter(value=jnp.array([1.0, 2.0]), momentum=jnp.array([3.0, 4.0]), name="w1")

def f(p):
    return jnp.sum(p.value ** 2) + jnp.sum(p.momentum ** 3)

grad_p = jax.grad(f)(p)

Step by step: tree_flatten gives leaves = ([1.0,2.0], [3.0,4.0]), aux = ("w1", False). grad sees f as a plain function of two arrays and differentiates each leaf independently:

∂f/∂value    = 2 * value    = 2 * [1.0, 2.0] = [2.0, 4.0]
∂f/∂momentum = 3 * momentum² = 3 * [9.0, 16.0] = [27.0, 48.0]

# tree_unflatten rebuilds a Parameter, reusing the SAME aux from step 1:
grad_p.value    == [2.0, 4.0]     # ∂f/∂value
grad_p.momentum == [27.0, 48.0]   # ∂f/∂momentum
grad_p.name     == "w1"          # unchanged — never touched by grad
grad_p.frozen   == False          # unchanged — never touched by grad
If you tried to differentiate through aux
Calling something like len(p.name) inside f would fail or be silently meaningless — grad has no mechanism to differentiate through a string, because strings never become leaves. Only what tree_flatten puts in leaves is visible to differentiation.

Retracing triggers: shape, dtype, AND pytree structure

"Shapes must be static" really means: across repeated calls to the same jitted function, the shape/dtype/pytree-structure of the arguments must stay identical, or you pay a fresh trace+compile — silently, no error, just slower.

@jax.jit
def f(x):
    return x * 2

f(jnp.ones((3,)))      # trace #1 — compiles for shape (3,), dtype float32
f(jnp.ones((3,)))      # reuses compiled version — same shape/dtype
f(jnp.ones((5,)))      # trace #2 — NEW shape (5,) → recompiles
f(jnp.ones((3,), dtype=jnp.int32))  # trace #3 — same shape, different DTYPE → recompiles

# pytree inputs: JAX checks shape/dtype of EVERY leaf, plus the pytree structure itself
f({"a": jnp.ones((3,)), "b": jnp.ones((2,))})  # trace #1
f({"a": jnp.ones((3,)), "b": jnp.ones((2,))})  # same structure+shapes → reuses
f({"a": jnp.ones((3,))})                        # DIFFERENT structure (missing "b") → recompiles
jit traces your Python code as-written — it doesn't fix bugs
f({"a": ..., "b": ...}) with return x * 2 doesn't "recompile weirdly" — it raises TypeError: unsupported operand type(s) for *: 'dict' and 'int', because Python dicts don't support multiplication. Tracing just runs your code once with tracers standing in for arrays; it never rewrites the logic. To operate on every leaf of a pytree, use jax.tree.map: 
def f(x):
    return jax.tree.map(lambda leaf: leaf * 2, x)

f({"a": jnp.ones((3,)), "b": jnp.ones((2,))})
# {"a": array([2.,2.,2.]), "b": array([2.,2.])}

This is exactly why in SlidingWindowSampler, every batch yielded has the same (batch_size, seq_len) shape — that consistency is what lets the training step get jitted once and reused for every batch, instead of recompiling every iteration.
