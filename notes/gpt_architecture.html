GPT Architecture Walkthrough

Every component you built, in the order data flows through them, with the actual code and why each piece exists.

Big picture

A GPT model turns a sequence of token ids into a probability distribution over the next token, for every position in the sequence simultaneously. The path:

token_ids (b, seq_len)
↓ Embedding — look up + add position
x (b, seq_len, embed_dim)
↓ GPTBlock × N — attention + feedforward, each with residuals
x (b, seq_len, embed_dim) ← same shape the whole time
↓ LayerNorm + Linear
logits (b, seq_len, vocab_size)
The one shape invariant to hold onto
From the moment embeddings are produced until the final output head, every intermediate tensor is (batch, seq_len, embed_dim). Attention mixes information across the seq_len axis; feedforward transforms within the embed_dim axis. Nothing changes the shape until the very last linear layer projects embed_dim → vocab_size.

Config used across the pipeline

CONFIG = {
    'vocab_size':    1000,   # size of output distribution — from BPE tokenizer
    'embed_dim':     64,     # dimensionality of each token's vector
    'max_seq_len':   256,    # longest sequence positional embeddings support
    'num_heads':     4,      # attention heads (64 / 4 = 16 dims per head)
    'input_dim':     64,     # must equal embed_dim — attention reads embeddings directly
    'output_dim':    64,     # must equal embed_dim — so residual add (x + shortcut) works
    'scaling_factor': 4,     # FeedForward hidden layer is 4x wider than embed_dim
    'dropout':       0.1,    # regularization inside GPTBlock
    'eps':           1e-5,   # LayerNorm numerical stability constant
    'num_of_blocks': 2,      # how many GPTBlocks stacked
}
Why input_dim == output_dim matters
GPTBlock does x = x + shortcut after both attention and feedforward. That elementwise add requires the output shape to exactly match the input shape — so output_dim must equal embed_dim. If you ever add a projection that changes width mid-block, you'd need to project the shortcut too.

1. Embedding

transformer/embedding.py

Converts integer token ids into learned vectors, and adds a learned vector per position so the model can tell token order apart (attention itself has no sense of order).

class Embedding(nnx.Module):
    def __init__(self, vocab_size, dimensions, max_seq_len, rngs: nnx.Rngs):
        self.embed = nnx.Param(
            jax.random.normal(rngs.params(),(vocab_size,dimensions))*0.02
        )
        self.positional = nnx.Param(
            jax.random.normal(rngs.params(),(max_seq_len,dimensions))*0.02
        )

    def __call__(self, token_ids_batch):
        embeddings = self.embed[token_ids_batch]
        positions = token_ids_batch.shape[1]
        positional_encodings = self.positional[:positions]
        return embeddings + positional_encodings

Shape trace

StepExpressionShape
Inputtoken_ids_batch(2, 3) — 2 sequences, 3 tokens each
Table lookupself.embed[token_ids_batch](2, 3, 64) — fancy indexing pulls one row per token id
Position sliceself.positional[:3](3, 64) — first 3 rows of the position table
Outputembeddings + positional_encodings(2, 3, 64) — broadcasts (3,64) across the batch dim
Why *0.02
Scaling the random init down keeps embeddings small at the start of training — large initial values make the loss landscape harder to optimize early on. This is a standard GPT-2-style initialization trick.
Learned vs. sinusoidal (Phase 3 TODO)
This uses a learned positional table — a parameter that gets trained like any other. Modern models (LLaMA, GLM) use RoPE instead, which rotates query/key vectors based on position rather than adding a learned vector. RoPE generalizes to sequence lengths never seen in training; learned embeddings don't (you can't index past max_seq_len).

2. Scaled Dot-Product Attention

transformer/attention.py

For every token, decide how much to "attend to" every other token (including itself), then take a weighted average of their value vectors. The causal mask prevents a token from attending to tokens that come after it.

class ScaledDotProdAttention(nnx.Module):

    def __init__(self, input_dim, output_dim, rngs: nnx.Rngs):
        self.q = nnx.Param(jax.random.normal(rngs.params(),(input_dim,output_dim)))
        self.k = nnx.Param(jax.random.normal(rngs.params(),(input_dim,output_dim)))
        self.v = nnx.Param(jax.random.normal(rngs.params(),(input_dim,output_dim)))
        self.dropout = nnx.Dropout(0.2)

    def __call__(self, embeddings, rngs: nnx.Rngs):
        query = embeddings @ self.q.value
        key = embeddings @ self.k.value
        value = embeddings @ self.v.value
        attention_scores = query @ jnp.swapaxes(key, -1, -2)
        mask = jnp.tril(jnp.ones((attention_scores.shape[-1],attention_scores.shape[-1]), dtype=bool))
        attention_scores = jnp.where(mask,attention_scores,-jnp.inf)
        attention_weights = nnx.softmax(attention_scores/key.shape[-1]**0.5,axis=-1)
        attention_weights = self.dropout(attention_weights, rngs=rngs)
        attention = attention_weights @ value
        return attention

Shape trace (batch=2, seq_len=3, embed_dim=64)

StepExpressionShape
Inputembeddings(2, 3, 64)
Projectquery, key, value(2, 3, 64) each — @ (64,64) keeps last dim same
Scoresquery @ swapaxes(key,-1,-2)(2, 3, 3) — every token's score against every other token
Mask + softmaxattention_weights(2, 3, 3) — rows sum to 1 along axis=-1
Weighted sumattention_weights @ value(2, 3, 64) — back to embedding shape
Why swapaxes(-1,-2) instead of .T
key is (2, 3, 64) — a batch of matrices. .T reverses all axes, giving (64, 3, 2), which is wrong. jnp.swapaxes(key, -1, -2) swaps only the last two axes → (2, 64, 3), so (2,3,64) @ (2,64,3) → (2,3,3) — a proper batched matmul.

The causal mask, concretely

# for seq_len=3:
mask = jnp.tril(jnp.ones((3,3), dtype=bool))
# [[ True, False, False],
#  [ True,  True, False],
#  [ True,  True,  True]]

# row i = "what token i is allowed to see": only positions <= i
# jnp.where(mask, scores, -inf) sets disallowed positions to -inf
# softmax(-inf) = 0 → those positions get exactly zero attention weight
Why divide by key.shape[-1]**0.5
Without scaling, dot products grow with the dimensionality (more terms summed = larger variance), pushing softmax into regions with near-zero gradients. Dividing by sqrt(head_dim) keeps the scores at a consistent scale regardless of dimension — this is the "scaled" in "scaled dot-product attention".

Why attention_weights @ value, not value @ attention_weights

Matrix multiply only contracts the last axis of the left operand with the second-to-last axis of the right operand. Shapes: attention_weights is (..., seq, seq), value is (..., seq, head_dim).

# attention_weights @ value → (..., seq, seq) @ (..., seq, head_dim) = (..., seq, head_dim)
# row i of the result: output[i,:] = sum_j weights[i,j] * value[j,:]
#   "token i's output = weighted average of every token j's value, weighted by
#    how much token i attends to token j" — row i of weights holds query i's weights

# tiny numeric example, seq_len=2, head_dim=1:
attention_weights = [[0.7, 0.3],     value = [[10],
                      [0.2, 0.8]]              [20]]

# row 0: 0.7*10 + 0.3*20 = 13   ← token 0: mostly its own value, a bit of token 1's
# row 1: 0.2*10 + 0.8*20 = 18   ← token 1: mostly its own value
Why the reverse order breaks
value @ attention_weights gives (..., seq, head_dim) @ (..., seq, seq) — invalid unless head_dim == seq, since the inner dimensions (head_dim and seq) must match. Even in that degenerate case, it would contract over head_dim — mixing feature dimensions weighted by attention scores — instead of mixing tokens weighted by attention scores, which is the entire point of attention.

3. Multi-Head Attention

transformer/attention.py

Same idea as above, but split the embedding into several smaller "heads" that each learn to attend to different kinds of relationships (e.g. one head might track syntax, another might track long-range topic), then concatenate the results.

class MultiHeadAttention(nnx.Module):

    def __init__(self, input_dim, output_dim, num_heads, rngs: nnx.Rngs):
        assert output_dim % num_heads == 0, "output_dim must be divisible by num_heads"
        self.num_heads = num_heads
        self.head_dim = output_dim//num_heads
        self.q = nnx.Param(jax.random.normal(rngs.params(),(input_dim,output_dim)))
        self.k = nnx.Param(jax.random.normal(rngs.params(),(input_dim,output_dim)))
        self.v = nnx.Param(jax.random.normal(rngs.params(),(input_dim,output_dim)))
        self.dropout = nnx.Dropout(0.2)

    def __call__(self, embeddings, rngs: nnx.Rngs):
        b, tokens, _ = embeddings.shape
        query = embeddings @ self.q.value
        key = embeddings @ self.k.value
        value = embeddings @ self.v.value

        query = jnp.reshape(query, (b,tokens,self.num_heads,self.head_dim)).swapaxes(1,2)
        key = jnp.reshape(key, (b,tokens,self.num_heads,self.head_dim)).swapaxes(1,2)
        value = jnp.reshape(value, (b,tokens,self.num_heads,self.head_dim)).swapaxes(1,2)

        attention_scores = query @ jnp.swapaxes(key, -1, -2)
        mask = jnp.tril(jnp.ones((attention_scores.shape[-1],attention_scores.shape[-1]), dtype=bool))
        attention_scores = jnp.where(mask,attention_scores,-jnp.inf)
        attention_weights = nnx.softmax(attention_scores/key.shape[-1]**0.5,axis=-1)
        attention_weights = self.dropout(attention_weights, rngs=rngs)
        attention = attention_weights @ value
        attention = jnp.swapaxes(attention, 1, 2)
        return jnp.reshape(attention, (b,tokens, self.num_heads*self.head_dim))

Shape trace (batch=2, seq_len=3, embed_dim=64, num_heads=4, head_dim=16)

StepShapeWhat happened
After projection(2, 3, 64)same as single-head so far
Reshape(2, 3, 4, 16)split 64 into 4 heads of 16 each
swapaxes(1,2)(2, 4, 3, 16)bring heads next to batch so each head attends independently
Attention scores(2, 4, 3, 3)one 3×3 attention matrix per head
Weighted sum(2, 4, 3, 16)each head produces its own 16-dim output per token
swapaxes(1,2) back(2, 3, 4, 16)heads next to their own dims again
Final reshape(2, 3, 64)concatenate heads back into one embedding vector
Why swapaxes(1,2) before attention
Matrix multiply (@) always operates on the last two axes and treats everything before that as independent batch dims. Moving heads to axis 1 (next to batch) makes (b, heads, tokens, head_dim) so that query @ key.T computes attention within each head separately — heads never see each other's data, which is the whole point of splitting them.

reshape then swapaxes — why both steps, and in that order

Two separate jobs: reshape splits the embedding into heads, swapaxes repositions them so matmul batches over heads correctly.

# step 1 — reshape doesn't move data, just reinterprets the last axis (64) as (4, 16).
# arrays are row-major, so this correctly groups the first 16 numbers as head 0, next 16 as head 1...
query[b, t, :]  # shape (64,)
  = [ q0_0...q0_15 | q1_0...q1_15 | q2_0...q2_15 | q3_0...q3_15 ]
         head 0          head 1         head 2         head 3

reshape → query[b, t, h, :]  # shape (4, 16)
  query[b, t, 0, :] = q0_0...q0_15   # head 0's slice
# after reshape: (2, 3, 4, 16) — axis order (batch, tokens, heads, head_dim)

# step 2 — swapaxes(1,2) permutes axes (still no data movement):
# (2, 3, 4, 16) → (2, 4, 3, 16) — axis order (batch, heads, tokens, head_dim)
Why the swap is required
Before swap, last two axes are (heads, head_dim) — a matmul there would multiply across heads and head_dim, mixing different heads' features together, which is nonsense. After swap, last two axes are (tokens, head_dim) with (batch, heads) as independent loop dimensions, so query @ key.swapaxes(-1,-2) gives (2, 4, 3, 3) — one clean attention matrix per batch item per head, fully independent. Skipping the swap would blend information across heads before the attention weighting even happens — defeating the entire purpose of splitting heads.
Concrete example
Say token 0 is "cat". Head 1 might learn to attend strongly to nearby adjectives ("the ___"), head 2 might learn to attend to the verb governing it ("___ sat"). Splitting into heads lets these different relationship types be learned in parallel subspaces instead of forcing one attention pattern to capture everything.

4. LayerNorm

transformer/layer_norm.py

Normalizes each token's vector independently (across its own embed_dim axis) to zero mean and unit variance, then applies a learned scale and shift. Stabilizes training by keeping activation magnitudes consistent as they flow through many stacked blocks.

class LayerNorm(nnx.Module):
    def __init__(self,eps,embed_dim):
        self.eps = eps
        self.scale = nnx.Param(jnp.ones(embed_dim))
        self.shift = nnx.Param(jnp.zeros(embed_dim))

    def __call__(self, embeddings):
        mean = jnp.mean(embeddings, axis=-1, keepdims=True)
        var = jnp.var(embeddings, axis=-1, keepdims=True)
        norm = (embeddings-mean)/jnp.sqrt(var+self.eps)
        return self.scale.value*norm + self.shift.value

Worked example — one token, embed_dim=4

x = [2.0, 4.0, 4.0, 6.0]

mean = (2+4+4+6)/4 = 4.0
var  = ((2-4)² + (4-4)² + (4-4)² + (6-4)²) / 4 = 2.0
norm = (x - 4.0) / sqrt(2.0 + 1e-5)
     ≈ [-1.414, 0.0, 0.0, 1.414]

# then scale (init=ones) and shift (init=zeros) are applied —
# at initialization this is a no-op, but they become learned during training
keepdims=True — why it matters
embeddings has shape (2,3,64). Without keepdims=True, jnp.mean(..., axis=-1) gives shape (2,3) — the reduced axis disappears entirely. (embeddings - mean) would then try to broadcast (2,3,64) against (2,3), which fails (shapes don't align from the right). With keepdims=True, mean has shape (2,3,1), which broadcasts cleanly against (2,3,64) — the single value at position [i,j,0] is subtracted from all 64 elements at [i,j,:].
Pre-norm vs post-norm
This codebase applies LayerNorm before attention/feedforward (see GPTBlock below), not after. Pre-norm keeps gradients flowing more directly through the residual path across many stacked blocks — the modern standard (GPT-2 onward), versus the original Transformer paper's post-norm.

5. FeedForward

transformer/feed_forward.py

After attention mixes information across tokens, FeedForward processes each token's vector independently, expanding it to a wider hidden dimension, applying a nonlinearity, then projecting back down. This is where most of a transformer's raw parameter count and "knowledge capacity" lives.

class FeedForward(nnx.Module):
    def __init__(self, embed_dim, scale_dim, use_bias, rngs: nnx.Rngs):
        self.linear1 = nnx.Linear(embed_dim,scale_dim,use_bias=use_bias,rngs=rngs)
        self.linear2 = nnx.Linear(scale_dim,embed_dim,use_bias=use_bias,rngs=rngs)

    def __call__(self,embeddings):
        x = self.linear1(embeddings)
        x = nnx.gelu(x)
        return self.linear2(x)

Shape trace (embed_dim=64, scaling_factor=4 → scale_dim=256)

StepShape
Input(2, 3, 64)
After linear1(2, 3, 256) — expand 4x
After GELU(2, 3, 256) — nonlinearity, shape unchanged
After linear2(2, 3, 64) — project back down to embed_dim
Why expand then contract
The wider intermediate layer gives the network more "room" to compute nonlinear combinations of the input features before compressing back to embed_dim. This expand-nonlinearity-contract pattern (also called an MLP block) is where transformers store most factual/associative knowledge — much more of it lives here than in the attention weights.
Phase 3 upgrade — SwiGLU
LLaMA/GLM replace plain GELU with SwiGLU, which uses a gating mechanism (two parallel linear projections, one gating the other) — better quality per parameter, at the cost of one extra linear layer.

6. GPTBlock

transformer/gpt_block.py

Combines attention and feedforward into one repeatable unit, each wrapped with pre-norm and a residual ("shortcut") connection. Stack N of these to make the full model.

class GPTBlock(nnx.Module):
    def __init__(self, config, rngs: nnx.Rngs):
        self.norm1 = LayerNorm(config['eps'], config['embed_dim'])
        self.attention = MultiHeadAttention(config['input_dim'], config['output_dim'], config['num_heads'], rngs)
        self.norm2 = LayerNorm(config['eps'], config['output_dim'])
        self.feed_forward = FeedForward(config['output_dim'], config['scaling_factor']*config['output_dim'], False, rngs)
        self.dropout =  nnx.Dropout(config['dropout'])

    def __call__(self, x, rngs: nnx.Rngs):
        shortcut = x
        x = self.norm1(x)
        x = self.attention(x, rngs)
        x = x + shortcut

        shortcut = x
        x = self.norm2(x)
        x = self.feed_forward(x)
        x = self.dropout(x,rngs=rngs)

        return x + shortcut
x ──┬──────────────────────────────┐
     │ norm1 → attention ──────────┤ (+) ──┬──────────────────────┐
                                    │ norm2 → ff → dropout ─┤ (+) ── output
Why the residual (shortcut) connection exists
Without x + shortcut, gradients would have to flow back through every attention and feedforward operation in every stacked block, and could vanish (shrink toward zero) after enough layers. The residual gives gradients a direct, unimpeded path back to earlier layers — this is what makes 12, 32, or 96-layer transformers trainable at all.

7. Model

transformer/model.py

Wires everything together: embed the tokens, run them through N stacked GPTBlocks, apply a final LayerNorm, then project to vocabulary size to get logits.

class Model(nnx.Module):
    def __init__(self, config, rngs: nnx.Rngs):
        self.embedding = Embedding(config['vocab_size'], config['embed_dim'], config['max_seq_len'], rngs)
        self.gpt_blocks = nnx.List([GPTBlock(config, rngs) for _ in range(config['num_of_blocks'])])
        self.layer_norm = LayerNorm(config['eps'], config['embed_dim'])
        self.linear = nnx.Linear(config['embed_dim'], config['vocab_size'], rngs=rngs)

    def __call__(self, x, rngs: nnx.Rngs):
        x = self.embedding(x)
        for block in self.gpt_blocks:
            x = block(x, rngs)
        x = self.layer_norm(x)
        return self.linear(x)

Full shape trace (2, 3) token ids → (2, 3, 1000) logits

StageShape

After Embedding(2, 3, 64)
After GPTBlock 1(2, 3, 64)
After GPTBlock 2(2, 3, 64)
After final LayerNorm(2, 3, 64)
After output Linear(2, 3, 1000) — logits over vocab
Why nnx.List, not a plain Python list
Flax NNX walks a module's attributes to find params it needs to track for jit/grad. A plain Python list attribute is treated as static (invisible to the tracking system) — the blocks inside it would silently never get trained. nnx.List is a wrapper that makes its contents visible as part of the module's state.
What the logits mean
logits[b, t, :] is a length-1000 vector of unnormalized scores — one per vocab token — representing the model's prediction for what token comes after position t in sequence b. Apply softmax to turn it into a probability distribution; argmax (or sampling) picks the actual next token during generation.

8. BPE Tokenizer

tokenizers/bpe_tokenizer.py

Converts raw text to integers (encode) and back (decode). Byte-Pair Encoding starts from raw UTF-8 bytes (256 possible values) and iteratively merges the most frequent adjacent pair into a new symbol, building up a vocabulary of common substrings/words.

def train(self, text: str):
    file_ids = list(text.encode('utf-8'))         # raw bytes: 0-255
    for i in range(self.max_merges):            # max_merges=744 → vocab_size=1000
        pairs = self.create_pairs(file_ids)     # count adjacent pair frequencies
        if not pairs: break
        max_pair = max(pairs, key=pairs.get)    # most frequent pair
        self.pairs_dict[max_pair] = 256 + i     # assign it a new id
        file_ids = self.merge(file_ids, max_pair, 256 + i)  # replace all occurrences
    self.build_vocab()

Worked example

# text = "aaab", encoded as bytes: [97, 97, 97, 98]
# pass 1: pair (97,97) appears twice → most frequent → new id 256
#   merge: [256, 97, 98]   ('aa' merged wherever it appears)
# pass 2: pair (256,97) appears once, (97,98) appears once → tie, pick one, say (256,97) → id 257
#   merge: [257, 98]
# vocab now: {256: b'aa', 257: b'aaa', ...}
# "aaab" (4 bytes) compresses to 2 tokens: [257, 98]
MAX_MERGES = 744
Final vocab size = 256 base byte values + 744 merges = 1000, matching CONFIG['vocab_size']. This isn't a coincidence — the tokenizer's vocab size and the model's embedding table size must match exactly, since token ids index directly into self.embed.

9. Sliding Window Sampler

(your implementation)

Turns one long stream of token ids into many (input, target) training pairs for next-token prediction, where target is input shifted right by one position.

class SlidingWindowSampler:
    def __init__(self, seq_len, batch_size, token_ids, stride=1):
        inputs, targets = [], []
        for i in range(0, len(token_ids) - seq_len, stride):
            inputs.append(token_ids[i:i+seq_len])
            targets.append(token_ids[i+1:i+seq_len+1])
        self.inputs = np.array(inputs)     # (num_windows, seq_len)
        self.targets = np.array(targets)   # (num_windows, seq_len)
        self.num_batches = len(self.inputs) // batch_size
        self.batch_size = batch_size

    def shuffle(self):
        idx = np.random.permutation(len(self.inputs))
        self.inputs = self.inputs[idx]
        self.targets = self.targets[idx]

    def __iter__(self):
        for i in range(self.num_batches):
            start = i * self.batch_size
            end = start + self.batch_size
            yield (jnp.array(self.inputs[start:end]),
                   jnp.array(self.targets[start:end]))

Worked example — token_ids = [10,11,12,13,14,15], seq_len=3, stride=1

i=0: input=[10,11,12]  target=[11,12,13]
i=1: input=[11,12,13]  target=[12,13,14]
i=2: input=[12,13,14]  target=[13,14,15]
# range stops at len(token_ids) - seq_len = 3, so i=0,1,2 only
# at every position, target[j] = input[j] shifted one step ahead —
# "given tokens up to here, predict the very next one"
Why yield tuples of JAX arrays
__iter__ is a generator (uses yield) — batches are produced lazily, one at a time, only when the training loop asks for the next one, rather than materializing every batch in memory up front. Converting to jnp.array only at yield time keeps the bulk storage in cheap NumPy and only pays the JAX conversion cost for the batch currently in use.
